# Efficiency Cloud 3.3.1 — 静态安全复核记录

复核范围：用户提供的 3.3.0 项目 ZIP 中的前端、Supabase SQL 迁移、Edge Functions、HTTP headers 与 Service Worker。此记录是源码静态复核，不是渗透测试，也不代表已连接或扫描生产 Supabase 项目。

## 已修复的源码问题

### 高优先级
- 好友关系更新策略允许接收者直接更新整行记录；单靠 `WITH CHECK` 不能阻止其改写 requester 字段。已撤销客户端对 friendships 的 UPDATE 权限，改用 `respond_friend_request` RPC，并在数据库端校验接收者、待处理状态和允许的结果。
- profiles 的客户端写权限显式收紧为仅可更新 `handle`，避免客户端修改会员权益、邮箱或效率云 ID。

### 中优先级
- 好友申请 RPC 增加输入格式校验、双向待处理检查和每账户 24 小时 20 次上限。
- 聊天消息增加空白内容拒绝、发送者身份校验和每账户每分钟 20 条上限。
- 支付订单创建函数从通配符 CORS 改为 `APP_URL` / `ADDITIONAL_ALLOWED_ORIGINS` 来源白名单。
- 增加 CSP、COOP、CORP 等响应头。
- Service Worker 不再缓存任意同源 GET 请求，仅缓存静态资源，并排除带查询参数或 Authorization 的请求。

## 仍需在部署环境验证

- Supabase 项目真实 RLS 策略、表权限、默认权限、触发器与函数 owner。
- Auth 邮箱验证、密码策略、MFA、OAuth 回调 URL、会话有效期、邮件/短信供应商限流。
- 数据库迁移能否在现有数据上成功执行；尤其是历史消息是否存在空白正文。
- 两个以上测试账户的越权读写、好友申请滥用、消息速率限制和账号注销级联行为。
- 支付服务商签名规范、Webhook 重放/并发行为、退款和拒付同步、网关适配器实际实现。
- npm 依赖安全状态。当前归档没有 package-lock.json；部署前应在可信 CI 中生成并提交 lockfile，运行 `npm ci` 与 `npm audit`，核对修复版本后再升级。

## 重要限制

没有访问用户的 Supabase 项目、生产域名、支付商户账户或 OAuth 控制台；没有运行真实数据库迁移、动态扫描、渗透测试或支付沙箱。不能据此宣称线上漏洞已经全部消除。聊天当前仍不具备端到端加密、举报/屏蔽、自动审核或附件安全扫描。


## 3.3.2 账户恢复与邮件提醒补充审查
- 密码恢复继续由 Supabase Auth 的一次性恢复链接处理，不在本应用自行存储或验证密码。
- 恢复回调进入 `/?recovery=1`，用户在已验证会话中调用 `auth.updateUser({ password })` 设置新密码。
- 新登录与密码变更提醒通过 Edge Function 发送；收件地址取自经 Supabase Auth 验证的用户记录，不接受客户端指定收件人。
- 事件类型固定白名单；服务端按用户和事件类型每小时最多发送 3 封；用户可在账户中心关闭提醒。
- 邮件通知依赖 Resend 和 Supabase SMTP 的外部配置；本地静态检查不能证明真实邮件送达。
- 未覆盖 OAuth 提供商后台的所有安全事件、管理员操作、设备指纹识别或 IP 风险分析；不能将邮件提醒描述为完整入侵检测。
